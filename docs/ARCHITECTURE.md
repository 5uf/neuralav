# Neural-AV target architecture

This is the contract for the rebuild. Each phase must leave `cargo test --workspace`, `cargo check`, and `npm run build` green.

Two goals drive every choice:
1. **Smallest footprint.** Pure Rust and small data structures. No ClamAV, no ONNX/BERT, no Python. Report binary size and peak RSS with each engine change.
2. **Catch polymorphic AI malware** (BlackMamba-style). The payload is generated by an LLM at runtime and changes on every run, so hashes and payload signatures cannot see it. Detect what stays the same: the **carrier** and the **behavior**.

## Shape

```
UI (Tauri v2, unprivileged)  ── local socket, JSON lines ──►  neuralav-service (Rust)
  src-tauri/  thin client                                      crates/service/
  depends on crates/proto only                                 ├─ crates/engine  (static layers)
                                                               ├─ SQLite store + quarantine vault
                                                               ├─ behavior monitor (ETW / eBPF)
                                                               └─ updater (minisign-signed bundles)
```

Cargo workspace at the repo root. Members: `src-tauri`, `crates/proto`, `crates/engine`, `crates/service`.

- `crates/proto`: serde request and response enums shared by the UI and the service. No heavy dependencies.
- `crates/engine`: a library with no IPC and no UI.
  - `scan_file(path) -> Verdict`, `scan_tree(root, cb)`.
  - `Verdict { status: Clean | Suspicious | Malicious, reasons: Vec<Reason{layer, detail}>, sha256 }`.
- `crates/service`: binary `neuralav-service`.
  - Subcommands: `run` (daemon), `scan <path> [--json]` (one-shot CLI, used by tests and benchmarks), `version`.
  - Owns the SQLite DB (`rusqlite`, bundled), the quarantine vault, the behavior monitor and the updater.

## Detection layers

Run the cheapest layers first. A later layer runs only when an earlier one leaves the file undecided or flags it.

| # | Layer | Catches | Cost |
|---|---|---|---|
| 1 | SHA-256 allowlist and known-bad set: sorted array of truncated hashes, mmapped | Exact known files | MB-scale data, O(log n) |
| 2 | Own rule matcher (`aho-corasick` + import table; literal rules in `crates/engine/rules/sigs/` done). Replaced yara-x, whose wasmtime dependency is too heavy | Known strings and API sets, plus **carrier rules**: LLM endpoint or key + dynamic exec + capture or exfil | Per-file scan |
| 2b | Unpackers (PyInstaller PYZ/CArchive, then Nuitka) | Feed the embedded bytecode and strings to layer 2 | Only on packed files. **Status: PyInstaller CArchive done** (`pyinstaller.rs`, `miniz_oxide`; scripts first, entries get hash + literal scan, no unmarshalling; caps 4096 entries / 64 MiB read+inflated, duplicate (offset, length) once; hitting a cap with no detection is reported as an error "not fully scanned", never Clean, and no ratio-based verdict). Nuitka and PYZ member extraction not started |
| 3 | Static GBDT on EMBER v3-style features (EMBER2024 Apache-2.0 models), hand-rolled evaluator over a flat node array | Unknown variants | Under 0.5 MB model. Can output **Suspicious** only, never Malicious. **Status: done** (`gbdt.rs`, `pe.rs`, `pe_features.rs`, `authenticode.rs`; model `rules/models/ember2024_pe.navgbdt`, 447 KB, Windows PE only, threshold 0.95, uncalibrated). Parity with thrember is exact for groups 1-4; imports, pefile warnings and authenticode are close approximations (see module headers) |
| 4 | Lifter-lite: decode (`iced-x86` decoder only, ARM64 decoder) and Python bytecode, lift to a small IR, normalize, match API-call sequences per function and known-bad function fingerprints | What code can do (keyboard hooks, screen capture, webhook exfil, persistence) and code reused from known malware, even after junk insertion or register renaming | Disassembly. Only for files flagged by 1 to 3 |
| 5 | Runtime behavior correlation (service) | The generated payload itself, by its effects | Event stream, always on |

Rejected for footprint: yara-x (wasmtime + Cranelift), a full capa port, a decompiler to C, ClamAV (1.2 to 2.4 GiB RAM), neural nets. Behavior correlation (layer 5) gives the widest coverage against polymorphic and AI malware and is the core layer.

Layer 3 may affect verdicts only after it is trained on documented data and measured (TPR at a fixed FPR). EMBER2024 results show the limits of static ML: PR AUC 0.57 on malware that every AV missed at first, and AUC 0.76 for predicting behavior tags. Layer 5 is the main defense against AI malware.

### Layer 4: lifter

Pipeline:
1. Parse with `goblin`. Find code sections and entry points.
2. Decode with `iced-x86` (x86/x64) or an ARM64 decoder. For a PyInstaller carrier, decode the Python bytecode instead.
3. Recover functions and basic blocks by recursive descent from entry points and exports.
4. Lift each instruction to a small IR: `assign`, `load`, `store`, `call(api)`, `branch`, `ret`.
5. Normalize the IR so rewritten variants look the same: drop nops and dead stores, rename registers, fold constants, resolve import thunks to API names.
6. Match:
   - capa-rules subset: API sets and call sequences per function (for example, `SetWindowsHookExW(WH_KEYBOARD_LL)` + `GetKeyState` + a file or network write).
   - Fingerprints: a hash of each normalized function, compared against functions from known malware.
   - Carrier pattern: an HTTP call to an LLM host whose response reaches `exec`, `compile` or an executable allocation.

Limits:
- Packed or encrypted code shows only the unpacker stub. Unpack first (layer 2b), or leave it to layer 5.
- A payload that an LLM generates at runtime is not in the file. The lifter sees only the carrier, so layer 5 still has to catch the payload.

### Layer 5: behavior correlation

The service scores each process from an event stream. Example rule:

1. The process is not allowlisted (browsers, IDEs and chat apps are allowlisted).
2. The process resolves or connects to an LLM API host.
3. Within N seconds it does any of these: installs a keyboard hook or polls key state, captures the screen, starts an interpreter or runs dynamically loaded code, or posts to a webhook host.

When the score crosses a threshold, the service kills the process, quarantines its image, and records the events.

Event sources:
- Windows: user-mode ETW (`ferrisetw`): DNS-Client, Kernel-Process and TCP/IP providers. The service runs as admin.
- Linux: eBPF (`aya`) for connect, exec, and uprobes on `SSL_write`. Fallback: fanotify and `/proc` polling.
- macOS: Endpoint Security needs an Apple entitlement. Fallback: `proc_pidinfo` and network-table polling, which is weaker.

Without a signed kernel driver (Windows) or the ES entitlement (macOS), the service detects and kills. It cannot block before execution.

## Security rules (non-negotiable)

- The UI never names a path for a destructive action. Delete, quarantine and restore take an **id** issued by the service: a detection id or a quarantine id. Scan requests may take a path, and they are read-only.
- Quarantine works like this:
  1. Content is XOR-obfuscated with a fixed key so it cannot run or be indexed.
  2. It is stored as `<vault>/<sha256>.bin`.
  3. Metadata (original path, sha256, size, reasons, time) goes in SQLite.
  4. Restore refuses to overwrite an existing file and verifies the sha256 after decoding.
- Data dir per OS:
  - Windows: `%ProgramData%\NeuralAV`
  - Linux: `/var/lib/neuralav`
  - macOS: `/Library/Application Support/NeuralAV`
  - Dev and non-root runs: `NEURALAV_DATA_DIR`, or the per-user data dir.
- No shell scripts. No elevation prompts. No `unwrap()` on IO or user input in the engine or the service.
- Updates are applied only after `minisign-verify` passes against the public key compiled into the binary. On failure, the previous bundle stays.
- Tests use only EICAR (built at runtime) and a harmless AI-polymorph simulator. Never run real samples.

## Platform support matrix (target)

| Capability | Windows 10/11 | Linux (x86-64, ARM64) | macOS 13+ | Android | iOS |
|---|---|---|---|---|---|
| On-demand scan (layers 1 to 4) | yes | yes | yes | later (separate app) | no (sandbox) |
| Behavior correlation (layer 5) | yes (ETW) | yes (eBPF, fallback fanotify) | weak (polling) | — | — |
| Pre-exec blocking | no: needs a signed minifilter driver | possible: fanotify `FAN_OPEN_EXEC_PERM` as root (future) | no: needs the ES entitlement | — | — |
| Service install | Windows service (`windows-service`) | systemd unit | launchd plist | — | — |

## Phases

1. **Engine**: proto and engine crates, hash layer, the `scan` CLI. Python, `cpython` and the fake stats are removed.
1.5. **Static layers**: own rule matcher (literal-signature core done; replaced yara-x), PyInstaller reader, AI-carrier rules, GBDT evaluator (done: `scripts/ember_parity.py` compares features and scores against thrember + LightGBM), and a harmless simulator in `tests/` (asks an LLM for code that prints a string, then runs it with `exec`).
2. **Service + store**: SQLite, the quarantine vault, IPC, the UI as a client, and service install files.
3. **Behavior correlation**: ETW (Windows) and eBPF (Linux) event sources, the per-process scorer, kill and quarantine.
4. **Lifter-lite**: decoder, IR, normalizer, API-sequence rules and function fingerprints on flagged files.
5. **Updates**: signed rule, hash and model bundles.
6. **Verification**: test corpus, benchmark harness (size, RSS, scan speed, TPR/FPR), and `docs/TESTING.md`.
